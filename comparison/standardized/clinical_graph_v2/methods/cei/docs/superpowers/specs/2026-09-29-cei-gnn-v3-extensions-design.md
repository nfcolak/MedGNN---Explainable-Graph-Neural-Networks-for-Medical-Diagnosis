## 1. Scope and claim structure

Three improvement items (user decisions U5, U7, U8 and the §10 decisions of 2026-09-29) are built on top of **v3 arm C** (v2 additive pair mode + PLE + not-measured block, frozen K per v3 §11.2). Each item is one or two arms; each trained arm uses the same 10,000-row TRAIN sample, the same OLD-dev checkpoint selection, seeds 1234/2025/7, and is scored once per frozen checkpoint on the v3 screen fold. Each arm has its own claim: "arm X beats v3 arm C on this screen", decided by the v3 §6.2 rule with the multiplicity policy of §7 below. No arm is a validation, test, or clinical claim. None of the arms is combined into one "best CEI" after results are seen. There is no non-GNN reference row on the screen (v3 §11.1 U3; §3 below).

Fixed control: arm C's three frozen checkpoints (the winning-K checkpoints of v3 §11.2). Every extension arm binds the v3 K-freeze hash (`k_selection_sha256`, v3 §12.17), C's three checkpoint SHA-256 values and C's three `binding.json` SHA-256 values (`control_binding_sha256`, v3 §12.21).

Extension arms are outside the A/B/C superset schema (E17): E2d registers residual blocks C does not have, E6b registers a block C does not have, E2w changes every tensor's shape, E6a widens the relation/triple/payload tensors. The v3 obligation "identical named tensor shapes across arms" (v3 §9 item 7) applies to A/B/C only; every extension binding reports its own named parameter inventory and the diff against C's inventory (added tensors, widened tensors, unchanged tensors), plus the field `common_init_identical_to_c: true|false` of §2.2.

Dimensions used for every count below (recorded v2 full-run binding, `additive_seed1234/binding.json` of the run reported in `<repo>/.worktrees/_runs/run-v2-full-3/report.md`): vocabulary 391, node_dim 63, edge_dim 22, classes 10, triples 16 (`num_triples` = fitted 15 + 1, `train.py` line 629, `tensorize.py` lines 85–90), relations 15 (forward), token_dim 32, pair_rank 16, node types 8, hidden 128, layers 1; recorded total 92,300 parameters (`comparison/standardized/clinical_graph_v2/methods/cei/docs/cei-gnn-v2-pair-study-result-2026-09-29.md` line 16). Analytic counts in this spec reproduce that 92,300 exactly from `cei_gnn_v2.py` lines 101–119 (`<repo>/.worktrees/_runs/spec-ext-1/param_counts.py`; independently recomputed by rev-ext-1). v3 arm C adds the PLE projection `(K+1) × hidden` (bias-free, v3 §12.3) and the absence tables `2 × |universe| × 10` on top; those v3 counts are not yet known and must be read from the C binding, so all parameter numbers here are **v2-schema counts plus stated deltas**, not final v3 totals.

## 2. Item 2 — larger CEI model (U5, D10.1)

### 2.1 What the code supports today

- `PairEvidenceNetwork.__init__` takes no `layers` argument (`comparison/standardized/clinical_graph_v2/methods/cei_gnn_v2.py` lines 90–91). The node encoder is one `Linear(node_dim + token_dim + hidden, hidden)` followed by `LayerNorm` (lines 103–104) and one GELU + dropout in the forward pass (lines 178–179). There is no message passing; node, edge and pair votes are all computed from that single-layer `h`.
- The v2 adapter rejects any depth other than 1: `plugin_cei_gnn_v2.py` lines 35–36 raise `ValueError("CEI-GNN v2 supports layers=1 only")`. The v1 GraphXAI bridge also refuses `layers != 1` (`cei_graphxai.py` lines 191–192), but that bridge already refuses every method other than v1 `cei_gnn` (line 148), so the check is moot for v3.
- Width is free: `hidden` sizes every block (lines 100–118), and the runner accepts `--hidden` (`train.py` line 1074).

So `layers > 1` is **not supported** by `cei_gnn_v2.py`. Per v3 §7, v2 files stay byte-identical; the change lands in the new v3 method (`cei_gnn_v3`) only.

### 2.2 What must change (v3 core interface obligation; unit U3x of §9)

The v3 network takes an `encoder_depth ≥ 1` constructor argument (default 1 = v2/v3-C behaviour, bit-identical on identical weights). Depth `d > 1` appends `d − 1` node-local residual blocks `h ← h + Dropout(GELU(LayerNorm(Linear_w×w(h))))` after the v2 encoder and before `node_head`, edge and pair votes. Node-local means: no neighbour aggregation, so the CEI exact logit decomposition (v3 §4.3) is unchanged; each block adds `w² + w` (Linear) `+ 2w` (LayerNorm) parameters. The v3 adapter maps the runner's `--layers` to `encoder_depth` and no longer raises for `layers > 1`.

**RNG and initialisation parity for every extension arm (E6; extends v3 §12.11).** The v3 core initialises every named tensor from its own `torch.Generator` seeded by `(seed, qualified tensor name)`. Consequently an arm that adds a tensor (E2d residual blocks, E6b comorbid block) or widens a tensor (E6a: `relation_embedding`, `triple_embedding`, `edge_feature_projection`, registered at `cei_gnn_v2.py` lines 106–108 BEFORE the later common tensors) leaves every other tensor's initial values identical to C's for the same seed; the binding records `common_init_identical_to_c: true` for E2d, E6a, E6b and O. E2w changes every tensor's shape and is the stated exception (`common_init_identical_to_c: false`; "same seed" then means the same sample order and the same per-tensor generator seeds, not the same initial values). New blocks never touch the global RNG stream: the E2d residual dropout draws its mask from a dedicated generator (`torch.rand(shape, generator=g) < p`, scaled by `1/(1−p)`, training mode only), and the E6b block has no dropout and no other RNG operation. Therefore the global stream (node dropout at line 179, edge-MLP dropouts at lines 109–110, pair dropout at line 223, DataLoader shuffle seed at `train.py` line 873) is consumed exactly as in C, and the RNG-parity test asserts `torch.get_rng_state()` equality after construction and after three training-mode forwards for C vs E2d, E6a and E6b on the same batch.

### 2.3 Fixed arms (D10.1: both, no size search on the screen)

Two arms, fixed now. Both: same K, data, seeds, epochs (40), optimizer, checkpoint selection as C; only the named dimension differs.

| Arm | Definition relative to C | v2-schema parameter delta (analytic) | v2-schema total |
|---|---|---|---|
| **E2w** (width) | C with `--hidden 256`, `encoder_depth 1` | +177,792 | 270,092 (2.93× C's 92,300) |
| **E2d** (depth) | C with `--hidden 128`, `encoder_depth 2` | +16,768 (128² + 128 + 2·128) | 109,068 (1.18×) |

Justification. (i) The v2 CEI at 92,300 parameters is small next to the frozen ProtGNN reference of 399,884 (`train.py` lines 94–95); hidden 256 (270,092 + v3 blocks) stays below that reference and is the largest power-of-two width that does. Hidden 320 (395,852 before v3 blocks) is expected to exceed the reference once the v3 PLE and absence blocks are added (whether it does depends on K and |universe|, both unknown until the C binding exists; at K=8 the PLE projection adds 2,880 and the absence tables add 20·|universe|, E16); the choice of 256 is fixed regardless. (ii) The v2 selected epochs for the additive arm were 17, 24 and 30 of 40 and no arm selected the last epoch (`comparison/standardized/clinical_graph_v2/methods/cei/docs/cei-gnn-v2-pair-study-result-2026-09-29.md` lines 89–95), so the 40-epoch budget is not truncating training; the size question is capacity, not schedule, and the 40/patience-40 budget is kept for parity. (iii) Width scales every evidence block (node, edge, pair, PLE projection); depth adds only node-local nonlinearity. They answer different questions, so both are run rather than one blend (D10.1).

Active/inactive: both arms have all blocks active as in C; report total/active/inactive from the binding; never claim capacity parity with C.

### 2.4 Memory and runtime (estimate)

E2w doubles the width of every `[nodes, hidden]` and `[edges, hidden]` intermediate (`edge_source`/`edge_target` first layers, lines 109–110) and of the pair projection input; the pair intermediates `[Q, 16]` are unchanged (rank fixed). Estimate: ≤ 2× the v2 per-stage node/edge activation memory; the v2 measured peak RSS 2.63 GiB (v3 §6.3) is not a bound. Time: unmeasured; the v2 per-stage mean is 125.38 s (v3 §6.3), and E2w is expected to be slower by a factor between 1 and 3 (matrix work scales with `w` to `w²`); E2d adds one `w×w` product per node, expected ≤ 1.2×. Both must be measured in the approved smoke and reported, not guessed. The v3 §4.5 memory preflight applies at batch 128.

### 2.5 Decision rule and multiplicity

E2w vs C and E2d vs C: each the v3 §6.2 three-condition rule, family-corrected as in §7 (m = 5). Claim wording: "wider (deeper) CEI v3 beats CEI v3 C on this screen". A win does not identify whether width or depth is the mechanism unless both win.

### 2.6 TDD obligations (item 2)

1. `encoder_depth=1` reproduces C's forward bit-for-bit on identical weights; `encoder_depth=2` changes only `h` and keeps exact logit reconstruction within 1e-5 (v3 §4.3); residual dropout consumes no global RNG (state equality, §2.2).
2. Parameter accounting: analytic deltas above equal `parameter_count(model)` differences; `run_config()` records `hidden`, `encoder_depth`, totals, `common_init_identical_to_c`.
3. The v3 adapter accepts `layers=2` and the v2 adapter still raises for it (v2 byte-identical); bindings reject an E2 arm whose K-freeze hash or `control_binding_sha256` differs from C's.

## 4. Item 5 — validation-tuned per-class logit offsets (U7, D10.3)

### 4.1 Mechanism

For a frozen checkpoint with screen logits `z ∈ R^{n×10}`, an offset vector `δ ∈ R^10` changes the prediction to `argmax_c (z_c + δ_c)`. `δ` does not change the model, its checkpoint, or the logit decomposition; it is a decision-rule change, reported as a separate arm **O** = "C + δ".

### 4.2 Fitting protocol (validation fold; opened by U7 for this item only)

- **Checkpoints.** The three frozen arm-C checkpoints (winning K). Offsets are fitted on **C only** (D10.3; fitting on "the best extension arm" cannot be done without reading the screen and is rejected).
- **Validation scoring (E3, E7).** The full 4,254-row validation fold (v2 binding `counts.validation = 4254`) is encoded once per C checkpoint by the U4 fold encoder with `fold='validation'`, `allow_validation=True` and the **item-5 approval record**, and scored by the X3 validation scorer (`cei_v3_ext/validation_scoring.py`), which stores raw float32 logits (`logits.npz`), `y`, `subjects`, `sample_ids` and their SHA-256 in a new path. This is the first and only validation scoring in the v3 programme. The approval record is `<output_root>/item5_validation_approval.json` = {`allow_validation: true`, the user's G3 approval reference for item 5, the three C checkpoint SHA-256s, the validation ordered sample-ID hash, timestamp}; its SHA-256 is bound in every O record. Without that record the encoder raises for `fold='validation'`. `split == 'test'` rows are dropped before `encode_graph` unconditionally (v3 §12.7); test is never loaded.
- **Target and metric (E13).** Validation visit-level macro-F1 over the fixed ten labels, `zero_division=0`, computed as the UNROUNDED `weighted_macro_f1` of the v3 study module (v3 §12.20; numerically equal to `cei_v2_study.weighted_macro_f1`, `cei_v2_study.py` lines 652–661), applied to `argmax(z + δ)`. Ties are ties at full float64 precision; the runner's 6-decimal rounding (`train.py` lines 375–377) is NOT used here, and this choice is bound in the freeze record as `metric: weighted_macro_f1_unrounded`.
- **Optimizer (fixed; E13).** Coordinate ascent on an integer grid: `i ∈ {−20, −19, …, +20}`, `δ_c = i / 10` (41 values, step 0.1, stored and hashed as the integer `i`). Start `i = 0` for every class. One sweep visits classes in label order 0..9; for each class, set `i_c` to the grid value maximising validation macro-F1 with all other coordinates fixed; ties → the value with the smallest `|i_c|`, then the smaller (more negative) `i_c`. Exactly 5 sweeps, no early stop, no restarts, no other grid. One `δ` per checkpoint (per seed).
- **Freeze.** Each `δ` (as integers) is stored with its checkpoint SHA-256, the validation ordered sample-ID hash, the validation `logits.npz` SHA-256, grid, sweep count, metric name and the resulting validation macro-F1 (reported as a tuning score, not a result); the record's SHA-256 is bound before any screen read.

### 4.3 Screen comparison (E7)

Arm O = the same three C checkpoints with their `δ` applied to C's stored **raw float32 screen logits** (`logits.npz`, written by the U5 screen scorer next to `proba`, both hashed in the screen record; no re-inference). The O scorer refuses a C screen record without a logits hash and refuses a `δ` record whose checkpoint SHA-256 or approval-record hash does not match. `argmax(z + δ)` is evaluated on logits, never on `log(softmax)` (float32 softmax underflow would give −inf). Contrast **O vs C**, paired on identical checkpoints and screen rows, v3 §6.2 rule with §7 correction (m = 5). Wording: "validation-tuned per-class offsets improve CEI v3 C's screen macro-F1". A win says the class decision thresholds were mis-set for macro-F1 under the training weights, not that the model learned more.

### 4.4 Consequence for fold roles (binding)

From the first item-5 validation scoring onward, **validation is a tuning fold** of this programme. It can no longer be reported as a held-out result for **any** arm (A, B, C, E2w, E2d, E6a, E6b or O), because a reported model choice (`δ`) has been fitted on it. Any later held-out claim needs the closed test fold and a separate explicit approval; nothing here requests that. The screen remains the only decision fold; the OLD dev fold remains the selection fold.

### 4.5 Parameter, memory and runtime

Zero trainable parameters (10 fitted constants per checkpoint). Runtime: 3 validation inferences (about 4,254 rows each) plus 3 × 5 × 10 × 41 = 6,150 macro-F1 evaluations on cached logits — seconds; memory negligible. Estimate, unmeasured.

### 4.6 TDD obligations (item 5)

1. The fitter accepts only validation-labelled rows (rejects train/dev/screen/test IDs), runs exactly 5 sweeps over the integer grid in label order, is deterministic, uses the unrounded metric, and its tie rule is exercised; the U4 encoder refuses `fold='validation'` without the approval record (assertion, not import).
2. The freeze record hashes checkpoint, validation IDs, logits, approval record and `δ`; replay recomputes `δ` bit-for-bit.
3. Screen application: `δ = 0` reproduces C's screen predictions exactly from stored logits; the O scorer refuses an unbound or mismatched `δ` and a screen record without a logits hash; the test fold loader is never called (guard test).

## 5. Item 6 — `comorbid_with` and the bidirectional edge view (U8, D10.6)

### 5.1 How the graph and CEI v2 treat relations today

- Producer: `comorbid_with` links two prior-diagnosis nodes coded in the same past encounter and is emitted **in both directions** (`graph.py` lines 254–259: `edge(left, right, 'comorbid_with', True)` and `edge(right, left, ...)`), with no payload (no `delta`, `interval_hours`, `last_seen_hours`, `prior_encounters`). It is an INFORMATIVE relation (`__init__.py` lines 34–36). The loop runs over past encounters (`for stay, tokens in by_encounter.items()`), so a pair coded together in n encounters is emitted 2n times (E14).
- Tensorization: the bidirectional view appends a `rev:` edge only for `REVERSIBLE_RELATIONS` (`tensorize.py` lines 41–43), after the forward block (lines 348–358); `comorbid_with` is explicitly excluded because it is already symmetric (line 39). Relation vocabulary grows 15 → 24 and triples 16 → 31 (lines 76–93); `edge_attr` width grows from 22 to 31 (relation one-hot + 7 payload columns, line 359).
- CEI v2 edge block: per-edge context = relation embedding + triple embedding + payload projection (`cei_gnn_v2.py` lines 187–188); vote = `edge_source(h[src]) + edge_target(h[dst]) + edge_context_vote(context)` (line 190); gate = `sigmoid(edge_context_gate(context))` (line 191), a function of context only; messages summed to target nodes by `EdgeEvidenceAggregator` (`methods/cei_gnn.py` lines 10–23, `flow="source_to_target"`, `aggr="add"`), then per graph with denominator `1 + Σ gates` over ALL edges of the graph (lines 192–195, 204). There is no message passing: `h` never receives neighbour information.

Consequences. (a) A `comorbid_with` edge already produces two votes per directed record (one per direction), each **endpoint-additive** in `h_i` and `h_j` with a gate that is constant for every comorbid edge in the dataset (identical relation, triple and all-missing payload). The model cannot express "diagnosis i together with j" beyond the sum of the two diagnoses' own transforms. (b) The bidirectional view does nothing to `comorbid_with`. (c) For CEI, the bidirectional view's stated purpose — routing for message passing (`tensorize.py` lines 34–40) — does not apply; it adds one endpoint-swapped vote per reversible edge with its own `rev:` relation/triple embeddings, i.e. edge-vote symmetrisation, not information.

Aggregate count over the fixed 10,000-row TRAIN sample (read-only, counts only; script and output in `<repo>/.worktrees/_runs/spec-ext-1/count_comorbid.py` and `count_comorbid.out`): 4,359 graphs have a prior-diagnosis node, 3,534 have two or more, **3,307 graphs (33.1%) have at least one `comorbid_with` edge**; 34,712 directed `comorbid_with` records (7.1% of the 489,471 forward-view edge records). 17,356 = directed records / 2 is an **upper bound** on the number of unique unordered pairs (a pair emitted in n past encounters contributes 2n records; multiplicity is discarded by the dedupe rule of §5.3, while the edge block still sees every record) (E14); the largest single graph has 102 directed records (≤ 51 unique pairs). The reversible relations sum to 393,001 records, so the bidirectional view raises the edge count to about 882,472 (1.80×) over the sample.

### 5.2 Arm E6a — bidirectional view

Definition: C with `--edge-direction bidirectional`; everything else identical (K, data, seeds, selection). The relation table, triple table and payload projection grow with the view (`plugin_cei_gnn_v2.py` line 43 sizes relations from `relation_count`, `methods/base.py` lines 26–32); the v3 adapter passes `edge_direction` through unchanged. v2-schema delta: +4,224 parameters (9 × 128 relation rows + 15 × 128 triple rows + 9 × 128 projection columns), total 96,524 before v3 blocks; all active. Under the per-tensor generator rule of §2.2 the widened tensors receive new initial values while every other tensor's initial values equal C's. Preprocessing state is direction-free (forward triples are reused, `tensorize.py` lines 85–93, 446–453), so the same knot table, item universe, K and `preprocessing_sha256` apply and are asserted equal to C's. Memory/runtime estimate: edge intermediates scale with 1.80× edges; time expected between 1.0× and 1.8× the C stage; unmeasured.

GraphXAI. The edge mask has one entry per edge of the arm's own tensorization (`cei_gnn_v2.py` lines 153–155); for E6a the list is `[forward block | reverse block]` (`tensorize.py` line 350: appended strictly after the forward block so forward ids are stable). Therefore the v3 §4.5 rule ("preserve original edge order, list and mask shape exactly") applies to the bidirectional list: mask length = F + R; a forward-length mask is rejected; the exporter records `edge_direction`, F and R; a reverse edge is attributed as its own item (relation `rev:*`) and is never merged into its forward edge — a forward+reverse sum may be reported only as a derived, labelled quantity. Masking a forward edge to zero does not mask its reverse twin.

### 5.3 Arm E6b — additive comorbid pair term (D10.6)

**Pair set.** From the forward edge list, take every edge whose relation is `comorbid_with` — the relation id is resolved by NAME from the bound `type_index_layout.edge_relation` of `preprocessing.json` (`tensorize.py` line 441), never the literal index (E15) — map it to the unordered pair `(min(src, dst), max(src, dst))` and deduplicate (`unique` over the pair tuples within the batch; both directions and every repeated encounter collapse to one pair, §5.1). Pairs never cross graphs (asserted via `batch_index`).

**Block (additive, dedicated parameters, own normalisation).** For each unique pair `(i, j)` in graph G:

    a_ij   = tanh(P_a h_i) + tanh(P_a h_j)          P_a: hidden × 16, no bias   (dedicated; NOT the v2 pair_projection)
    v_ij   = V_a a_ij + b_a                           V_a: 16 × 10, b_a: 10      (dedicated; NOT edge_source/edge_target/pair_vote)
    g_c    = sigmoid(γ_c)                             γ: one gate logit per class, shared by all comorbid pairs
    comorbid_Gc = Σ_pairs g_c v_ijc / (1 + Σ_pairs g_c)

added to the logits as a fifth block alongside node/edge/pair/absence (v3 §4.3 sum). Empty pair set → block exactly zero, denominator one. `return_parts` adds `comorbid_contributions` `[pairs, 10]`, `comorbid_pairs` `[2, pairs]`, `comorbid_gates` `[10]`, `comorbid_denominator` `[graphs, 10]`; reconstruction within 1e-5; existing keys and shapes unchanged. The block is symmetric in `(i, j)` by construction, contains no dropout and no other RNG operation (§2.2), and is implemented through the U3x `extra_blocks` protocol (§9) so the v3 core file is not edited. It is not an edge: it lives outside the GraphXAI edge mask like the absence block (v3 §4.5), and a zero edge mask removes only the edge block. **Parameter count** at hidden 128: `P_a` 128 × 16 = 2,048; `V_a` + `b_a` = 160 + 10 = 170; `γ` = 10; **+2,228** (v2-schema total 94,528 before v3 blocks); at hidden 256 it would be 4,276, but E6b is run at hidden 128 only.

**How E6b differs from the existing comorbid edge vote, and how it overlaps.** The edge block (`cei_gnn_v2.py` lines 187–195) already gives every directed `comorbid_with` record the vote `edge_source(h_src) + edge_target(h_dst) + edge_context_vote(ctx)` with the constant gate `sigmoid(edge_context_gate(ctx))`, so one unordered pair contributes `edge_source(h_i) + edge_target(h_j) + edge_source(h_j) + edge_target(h_i) + 2·edge_context_vote(ctx)` per encounter in which it was coded — an endpoint-additive, symmetric vote. E6b's `v_ij` is ALSO an endpoint-additive, symmetric function of `(h_i, h_j)`. The differences are exactly these four: (1) dedicated parameters `P_a`, `V_a`, `b_a`, `γ` that no other relation shares, whereas `edge_source`/`edge_target`/`edge_context_vote` are shared by all 15 relations (comorbid records are 7.1% of the edge records); (2) each unordered pair is counted once, not 2n times; (3) the denominator `1 + Σ_pairs g_c` normalises over comorbid pairs only, whereas the edge denominator `1 + Σ_all-edges gates` dilutes comorbid votes by every other edge of the graph; (4) a rank-16 `tanh` bottleneck. **Overlap, stated explicitly:** in function space the additive E6b term is a re-weighted, re-normalised, de-duplicated version of what the edge block can already express for comorbid records; it adds no interaction term (no "i together with j" capability, which §5.1(a) identified as the missing one). The user chose the additive form on 2026-09-29 knowing this (D10.6). **Consequence for interpretation, stated now:** a null result for E6b vs C is expected to be hard to distinguish from "the shared edge block already captures the additive comorbid signal" — the study cannot separate "no additive comorbid signal beyond the edge block" from "no comorbid signal at all"; a positive result is attributable to the four differences above only, not to an interaction. The v2 within-visit product result (`interaction_useful=false`, complaint/measurement/vital pairs) is not evidence either way about diagnosis pairs; it is simply not tested here.

Attribution caveat (E15): GraphXAI edge importance for a comorbid edge does not include the E6b term (the pair set is derived from the edge list but the block is outside edge masks), so per-edge importances under-attribute comorbid pairs; the model's own `comorbid_contributions` are the attribution channel for E6b.

Memory: ≤ 51 unique pairs per graph in the sample (vs. up to 5,741 within-visit pairs, v3 §4.5), negligible. Time ≈ C stage; unmeasured.

E6a and E6b are separate arms; a combined "both" arm is not run (it would be a third contrast and cannot be attributed).

### 5.4 Decision rules

E6a vs C and E6b vs C: v3 §6.2 rule with §7 correction (m = 5). Wording: "the bidirectional edge view (the additive comorbid pair term) improves CEI v3 C on this screen". Secondary, non-decisive: the patient-mean absolute-evidence share of the comorbid block (E6b), defined as in v3 §6.2 for the absence block, and the fraction of screen graphs with a non-empty comorbid pair set.

### 5.5 TDD obligations (item 6)

1. Pair extraction: relation resolved by name from the bound layout; both directions and repeated records collapse to one unordered pair; non-comorbid relations are ignored; pairs never cross graphs; a graph without comorbid edges yields an exact-zero block and denominator one.
2. E6b reconstruction with the new keys; existing keys and shapes unchanged; parameter delta equals the analytic +2,228; block is outside the edge mask (zero mask leaves it intact); no global RNG consumption (state equality vs C after three training forwards); symmetry `v_ij == v_ji`.
3. E6a: bidirectional tensorization of a fixture graph yields F + R edges with the reverse block appended after the forward block; mask length F + R accepted, length F rejected; K-freeze, `control_binding_sha256` and preprocessing hashes equal C's.

## 7. Multiplicity policy (fixed before any result; D10.4)

Five primary contrasts share one control (C) on one screen: **E2w, E2d, O, E6a, E6b vs C → m = 5**. Conditions 1 and 2 of v3 §6.2 (per-seed strict win; seed-mean win) are unchanged and uncorrected. Condition 3 is Bonferroni-corrected with m = 5, using the same 1,000 paired patient-cluster bootstrap resamples with seed 2026 (identical patient draws for every arm and seed, v3 §6.2).

**Exact bound rule (E5).** In the extension family both bounds are order statistics of the sorted 1,000 averaged deltas with 0-based index `floor(1000 * p) - 1`; nominal p = 0.025 → `sorted[24]` (the 25th smallest); corrected p = 0.025 / 5 = 0.005 → `sorted[4]` (the 5th smallest). The decision requires the corrected bound `sorted[4]` to be strictly above zero. The nominal bound `sorted[24]` is reported next to it as "nominal" (D10.4). The v3 C-vs-A decision keeps `np.quantile(values, 0.025, method='linear')` as its bound (v3 §12.20, F20); the extension report also prints that linear-quantile value for every extension contrast for cross-reading, labelled as such and never used for the decision. Empirical tail mass of the corrected bound: 5/1,000 = 0.005 = 0.025/5 exactly.

Wording: an arm passing all three corrected conditions "beats C on this screen (family-corrected, m = 5)"; an arm passing only with the nominal bound is reported as "nominal win, not family-corrected" and is not a positive decision. No contrast may be added to or removed from the family after any screen result is seen; if an arm is not run, m stays 5 (conservative). This is a deliberate choice of a crude but transparent correction over none; 1,000 resamples make the corrected tail coarse (5 samples), which is accepted and stated rather than fixed by changing the pre-registered resample count.
